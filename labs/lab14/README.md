# Лабораторна робота №14 — Stateful Flow Orchestration (DOU Vacancies)

### 1. Опис Use Case
Метою роботи є перехід від простого виклику інструментів (ad-hoc single-agent) до керованого конвеєра зі збереженням стану (**Stateful Flow**) для аналізу та структурування ІТ-вакансій з платформи DOU.ua. Платформа приймає сирий текст вакансії, автоматично визначає її тип, витягує стек технологій та досвід, валідує дані та стабільно експортує фінальний результат.

### 2. Етапи Оркестрації (Flow Steps)
Пайплайн працює з єдиним мутабельним об'єктом стану (`FlowState`) і проходить через 6 обов'язкових кроків:
1. **Ingest:** Приймання сирого тексту, нормалізація (видалення зайвих пробілів/символів) та генерація унікального `case_id`. Відсіювання порожніх запитів на ранньому етапі.
2. **Route:** Детермінована маршрутизація на основі ключових слів. Якщо вакансія нетехнічна (Sales, HR, Recruiter), вона маркується як `non_tech_skip` і йде в обхід LLM, що кардинально економити токени та час обчислень.
3. **Execute:** Для технічних вакансій викликається локальна LLM (`Llama-3-8B-Instruct`), яка витягує дані строго за заданою схемою.
4. **Validate:** Перевірка структури JSON через бібліотеку `jsonschema` та логічний аналіз даних (відловлювання нереалістичних галюцинацій моделі, наприклад, 50 років досвіду).
5. **Fallback:** Безпечне відновлення (Safe Failure). Якщо LLM повернула зламаний синтаксис або впала з помилкою, запускається детермінований RegEx-патерн для витягування років досвіду з тексту, а запис маркується прапорцем `needs_manual_review`.
6. **Export:** Формування фінального, передбачуваного JSON-контракту для збереження в базу даних, незалежно від того, чи успішно пройшов пайплайн, чи впав на якомусь етапі.

### 3. Технічний стек та Модель
* **LLM Двигун:** Локальна модель `unsloth/llama-3-8b-Instruct-bnb-4bit` (4-бітне квантування для запуску на Colab GPU).
* **Валідація:** Бібліотека `jsonschema` для перевірки типів даних та обов'язкових полів.
* **Логування:** Модуль `src/flow_logger.py` для запису повного стану виконання кожного кроку у файл `flow_logs_lab14.jsonl`.

### 4. Метрики та Результати (на 10 Test Cases)
* **Flow completion rate:** ~80% (кейси, які успішно структурувалися або були свідомо та безпечно оброблені роутером).
* **Export valid rate:** 90% (зовнішні системи гарантовано отримують стабільний JSON-об'єкт навіть для спаму чи порожнього вводу).
* **Safe Failure Rate:** 100% перехоплення критичних збоїв без падіння всього скрипта.

### 5. Головний інженерний висновок
Впровадження архітектури Stateful Flow повністю вирішило головну проблему попередньої лабораторної роботи (Lab 12) — **Unnecessary Tool Calls (Зайві виклики)**. Завдяки кроку детермінованого роутингу, нетехнічні вакансії більше не навантажують LLM. Ізоляція стану в об'єкті `FlowState` зробила код чистим, а етапи валідації та fallback гарантують, що в підсумкову базу даних ніколи не потраплять синтаксичні помилки або грубі галюцинації моделі.
