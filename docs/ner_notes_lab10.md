# NER Notes: Lab 10 (DOU Vacancies)

## 1. Який pipeline вибрано
Використано бібліотеку **spaCy** з базовою англомовною моделлю `en_core_web_sm`. Вона обрана через наявність компонента `EntityRuler`, що ідеально підходить для побудови гібридних пайплайнів (модель + правила). Англомовна модель використана тому, що переважна більшість ключових ІТ-термінів пишуться англійською.

## 2. Які сутності він уміє з коробки
Базова модель розпізнає класичні загальні сутності: `PERSON` (люди), `ORG` (організації/компанії), `GPE` (міста/країни), `DATE` (дати), `MONEY` (гроші), `CARDINAL` (числівники) тощо. 

## 3. Які доменні сутності для вашого корпусу важливі
Для аналізу ІТ-вакансій DOU критично важливими є дві нові кастомні сутності:
* `TECH`: Технології, мови програмування, фреймворки (Python, React, Docker).
* `EXPERIENCE`: Вимоги до досвіду роботи (3+ years, 2 років).
Також важливим є правильне витягування специфічних ІТ-зарплат під лейблом `MONEY` (напр. $4k).

## 4. Які правила ви додали
В `EntityRuler` додано 3 типи гібридних правил:
1. **Словник технологій (Exact Match):** Задано список ключових хард-скілів (Python, Node.js, CI/CD, AWS) під лейблом `TECH`.
2. **Патерн досвіду (Token RegEx):** Правило `[число] + [опціональний +] + [years/роки]`, що маркує це як `EXPERIENCE`.
3. **Boundary fixes для грошей:** Три структурні патерни для виправлення помилок базової моделі на ІТ-зарплатах (`$ + цифра + k`, `цифра - цифра + USD`).

## 5. Що стало краще після правил
Гібридний пайплайн показав драматичне покращення:
* **Precision/Recall для TECH:** Зріс від нуля до майже 100% на тестовій вибірці. Зникли галюцинації (Type Errors), коли базова модель позначала "Java" чи "C++" як людей (`PERSON`).
* **Experience:** Повністю вирішено проблему ігнорування або розпізнавання досвіду як абстрактної дати (`DATE`).
* **Money boundaries:** Зарплатні вилки тепер витягуються повним блоком (span), а не лише як перша цифра.

## 6. Які помилки залишилися
* **Невідомі компанії:** Якщо назва ІТ-компанії дуже рідкісна або пишеться незвично, базова модель її пропускає (потрібно вчити Named Entity Recognition на нових даних).
* **Tokenization issues:** Якщо технології написані через слеш без пробілів (напр., `Python/Django`), точний словник може дати збій.

## 7. Що б ви фіксили далі
* **Розширення словника TECH:** Інтегрував би зовнішню базу даних (наприклад, StackOverflow tags), щоб автоматично підтягувати тисячі існуючих фреймворків без ручного вводу.
* **Soft Skills Extraction:** Додав би правила для витягування абстрактних навичок (Leadership, Communication) за допомогою POS-тегів (прикметник + іменник) та PhraseMatcher.
* **Training NER:** Для кращого розпізнавання нових компаній донавчив би шар NER на розмічених ІТ-текстах.
