# Crew Notes: Multi-Agent Extraction System (Lab 13)

## 1. Який use case обрано
Екстракція структурованих даних (JSON) з неструктурованих текстів ІТ-вакансій (з фокусом на український ринок, наприклад DOU.ua). Мета: отримання чистих метаданих (посада, досвід, скіли, англійська) для подальшої аналітики.

## 2. Які агенти є в crew
У нашому пайплайні залучено 4 агенти:
1. **Triager**
2. **Extractor**
3. **QA Reviewer**
4. **Repair Agent** (працює у зв'язці з модулем Fallback)

## 3. Роль кожного агента
*   **Triager:** Класифікує вхідний текст (ІТ-вакансія чи сміття/інший текст), визначає базову маршрутизацію.
*   **Extractor:** Витягує цільові поля у форматі JSON згідно з жорсткою схемою.
*   **QA Reviewer:** Виступає "контролером якості". Аналізує згенерований JSON на предмет помилок схеми, галюцинацій та нестиковок із початковим текстом.
*   **Repair Agent:** Отримує фідбек від Reviewer-а та намагається точково виправити зламаний JSON (наприклад, змінити тип даних з float на int).

## 4. Правила делегування
*   **Вхід:** Текст передається Triager-у.
*   **Triager -> Extractor:** Якщо текст розпізнано як вакансію. Якщо ні — миттєвий Fallback (відхилення).
*   **Extractor -> Reviewer:** Згенерований JSON передається на перевірку.
*   **Reviewer -> Final:** Якщо вердикт `accept`.
*   **Reviewer -> Repair:** Якщо вердикт `repair_needed`.
*   **Reviewer -> Fallback:** Якщо знайдено критичні суперечності, потрібен `manual_review` або Repair не впорався з виправленням.

## 5. Що перевіряє Reviewer
*   **Відповідність JSON-схемі:** наявність обов'язкових полів.
*   **Типи даних:** наприклад, чи є `experience_years` цілим числом.
*   **Галюцинації:** чи не вигадав Extractor навички (skills), яких немає в тексті.
*   **Логічну консистентність:** пошук суперечностей (наприклад, вказано `is_remote: true`, хоча в тексті "робота виключно з офісу").

## 6. Коли спрацьовує fallback
Fallback (Safe Failure) спрацьовує у трьох випадках:
1. Triager відхиляє текст як "non-IT".
2. Reviewer знаходить суперечності, які вимагають ручного втручання людини.
3. Repair Agent не зміг виправити структуру JSON після спроби відновлення.
При Fallback система не падає (не кидає Exception), а повертає часткові дані (`partial_output`) та статус потреби в ручному рев'ю.

## 7. Що crew покращив порівняно з single-agent
*   **Надійність (Robustness):** Зникли падіння через type mismatch та битий JSON.
*   **Точність:** Значно знизився hallucination rate, бо Reviewer ловить вигадані скіли.
*   **Фільтрація:** Система перестала "натягувати сову на глобус" і намагатися парсити текст про "продаж гаража" як вакансію.

## 8. Де multi-agent підхід був зайвий
Для ідеально написаних, шаблонних вакансій без "підводних каменів". У таких простих кейсах Extractor і так робить все правильно з першого разу. Запуск Triager-а та Reviewer-а для таких текстів — це зайве витрачання токенів, часу та лімітів API (RPM).

## 9. Які помилки залишилися
*   Модель все ще може плутатися у складному описі досвіду (наприклад, "півроку комерції, рік фрілансу і два роки пет-проєктів" — важко звести до одного integer).
*   Проблеми з неоднозначним визначенням `is_remote` (коли є гібридний формат, а поле вимагає boolean).

## 10. Що б ви фіксили далі
*   **Оптимізація витрат:** Використав би швидші та дешевші моделі (наприклад, Llama-3-8B) для простих ролей (Triager, Reviewer), а важку модель (Llama-3-70B) залишив би тільки для Extractor та Repair.
*   **Few-Shot Prompting:** Додав би у промпт Extractor-а кілька складних прикладів (few-shot), щоб він краще розумів специфічний український ІТ-сленг (наприклад, "сіньйор помідор", "галера").
